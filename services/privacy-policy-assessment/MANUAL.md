# 운영 매뉴얼 — 개인정보처리방침 평가 서비스

버전 v0.1.0 · 소유: 로켓보안 · 개정 이력은 `improvement/DAILY_LOG.md`

이 매뉴얼은 **한 사람(또는 한 에이전트)이 처음부터 끝까지 수행할 수 있도록** 쓴다.
각 Phase는 입력 → 작업 → 산출 → 게이트 순서다. 게이트를 통과하지 못하면 다음 Phase로 가지 않는다.

---

## 0. 역할과 관점

한 명이 수행하더라도 아래 다섯 관점을 순서대로 바꿔 쓴다. 보고서의 각 문장은 어느 관점에서 쓴 것인지 구분 가능해야 한다.

| 관점 | 묻는 질문 | 산출물에서 맡는 부분 |
|---|---|---|
| 개인정보영향평가 전문가 | 개인정보가 어디서 들어와 어디로 가는가? 위험은 어디서 생기는가? | 흐름표·흐름도, 위험 식별 |
| ISMS-P 인증심사원 | 인증기준 3.1~3.5(개인정보 처리단계별 요구사항)와 1.x·2.x 관련 항목에서 결함인가? | 모의심사 보고서, 한줄결함 |
| 심사팀장 | 결함의 근거가 제3자에게 설명 가능한가? 과잉 지적은 아닌가? | 결함 검토회의(교차검증), 우선순위 |
| 변호사 | 법 조문·시행령·고시 어디에 걸리는가? 과태료·과징금 사유인가? | 법령 근거 표, 위험 등급 |
| 컨설턴트 | 고객이 내일 무엇부터 해야 하는가? 비용·기간은? | 경영진 요약, 조치 로드맵 |

## 1. Phase 0 — 접수 및 범위 확정 (0.5일)

**입력**: 기업명, 서비스 도메인, (선택) 기존 처리방침·흐름표·흐름도·인증서·조직도
**작업**
1. `scripts/new_case.sh "<기업명>" <도메인>` 으로 케이스 폴더 생성.
2. `cases/<케이스>/00_intake.md` 작성: 서비스 목록(웹·앱·오프라인), 인증 보유 여부(ISMS/ISMS-P/간편인증), 담당자, 계약 범위, 납기.
3. 기존 문서가 있으면 `cases/<케이스>/input/`에 보관하고 **고도화 모드**로 표시(신규 작성이 아니라 현행화·대조가 목표).
4. 법령 기준일 고정: 보고서 전체에서 사용하는 법령·고시 버전을 `checklists/law-watch.md`에서 확인하고 케이스에 기록.

**게이트 G0**: 범위·납기·고도화/신규 모드가 문서화됨. OSINT 수행 범위(도메인 목록)를 고객에게 서면 통지함.

## 2. Phase 1 — 공개정보 수집 (OSINT, 0.5~1일)

**원칙**: 비침투·수동(passive) 방식만. 로그인, 인증번호 요청, 계정 생성, 폼 제출, 취약점 스캔, 대량 요청 금지. 상세는 `security/access-control.md`.

**작업**
1. `scripts/osint_collect.sh <도메인> <케이스폴더>` 실행 → `osint/` 폴더에 결과 저장.
   - DNS·서브도메인(crt.sh 인증서 투명성 로그), WHOIS, robots.txt, sitemap.xml, 공개 HTTP 헤더
   - spiderfoot이 설치된 경우 passive 모듈만(`-m` 지정) 사용
2. 수동 확인(브라우저, 비로그인): 처리방침 URL 전부(서비스별·버전별), 회원가입 화면의 수집 항목·동의 문구, 앱스토어 설명의 권한·개인정보 라벨, 고객센터·채용·이벤트 페이지, SNS 로그인 버튼, 챗봇·상담 위젯, 오프라인 매장·전화 접수 안내.
3. 외부 신호: 과거 유출 공지, 개인정보위 처분 이력, 뉴스, 인증 현황(isms.kisa.or.kr).
4. 모든 항목에 **URL + 확인일시 + 캡처 파일명**을 남긴다. 캡처는 `osint/captures/`.

**산출**: `osint/00_collection-log.md` (무엇을 어디서 확인했는지), `osint/surface-inventory.md` (수집 접점 목록)
**게이트 G1**: 수집 접점 목록에 "확인함/미확인/접근불가" 상태가 모두 표시됨. 능동 행위가 하나도 없음을 체크리스트로 확인.

## 3. Phase 2 — 개인정보처리방침 평가 (1일)

**기준**: `checklists/policy-eval-checklist.md` (법 §30 기재사항, §30의2 평가 관점: 적정성·가독성·접근성, 시행령·고시·작성지침)
**작업**
1. 처리방침 원문을 `input/policy_<날짜>.md`로 저장(버전 이력 포함. 이전 버전이 공개되어 있으면 함께 저장해 개정 대조).
   - `scripts/fetch_policy.sh <도메인> <케이스폴더>`가 메인 페이지 푸터에서 방침 링크를 찾아 1회 GET → `input/policy_<날짜>.md`(출처 URL·확인일시·원본 해시 포함)와 `.html` 원본을 만든다. robots.txt 금지 경로는 받지 않는다. 이전 버전은 `scripts/fetch_policy.sh <이전버전URL> <케이스폴더>`로 같은 날 `_2` 접미사로 저장. 자동 변환본은 반드시 브라우저 화면과 대조한다.
2. 체크리스트 항목별로 `있음/없음/불명확/해당없음` 판정 + 근거 문장 인용(원문 그대로) + 조문.
3. 가독성: 목차·요약·라벨링(개인정보 처리 표시) 유무, 문장 길이, 전문용어 비율, 모바일 가독성.
4. 접근성: 첫 화면 링크 위치·명칭·글자 크기/색, 앱 내 접근 단계 수.
5. 정합성: Phase 1에서 확인한 실제 수집 항목·위탁사·제3자와 처리방침 기재 대조 → 불일치 목록.
6. 최신성: `law-watch.md`의 최근 개정 사항(국외이전, 민감정보 공개 가능성, 자동화된 결정, 영상정보처리기기 등) 반영 여부.

**산출**: `templates/03_policy-evaluation-report.md` 채움 + `templates/02_privacy-policy.md`로 개정안(또는 신규안) 작성. 개정안은 **변경 대조표**(기존→개정, 사유, 근거) 포함.
**게이트 G2**: 모든 "없음/불명확" 판정에 조문·근거 인용이 있음. 개정안의 모든 문단이 체크리스트 항목에 매핑됨.

## 4. Phase 3 — 수집·처리 경로 전수 분석 (1일)

**기준**: `checklists/flow-analysis-checklist.md`
**작업**
1. 경로 유형별 전수조사: 온라인 가입/주문/문의, SNS 유입(소셜 로그인·광고 픽셀·채널톡 등), 오프라인(매장·행사·전화·서면), 협력사·제휴, 위탁(결제·배송·CS·마케팅·클라우드), 제3자 제공, 국외이전(해외 SaaS 포함), 자동수집(쿠키·SDK·로그).
2. 경로마다 수집 항목(필수/선택), 수집 근거(동의/계약/법령), 목적, 보유기간, 저장 위치, 접근 부서, 암호화 여부(확인 가능 범위), 제공·위탁 상대, 파기 시점.
3. 공개정보로 알 수 없는 항목은 **"확인 필요 — 인터뷰 질문"**으로 분리해 `interview-questions.md`에 모은다.

**산출**: `templates/04_data-flow-table.md`(흐름표 초안 + 평가), `templates/05_data-flow-diagram.md`(흐름도 초안 Mermaid + 평가)
**게이트 G3**: 흐름표의 모든 행에 출처(화면/문서/인터뷰)가 있음. 흐름도의 모든 노드가 흐름표 행과 1:1 대응.

---

## 5. Phase 4 — 모의심사 (1일)

**기준**: ISMS-P 인증기준 3.1~3.5 전 항목 + 관련 1.x(정책·자산·위험), 2.x(접근통제·암호화·로그) 항목
**작업**
1. 항목별 판정: 적합 / 결함 후보 / 확인 필요(운영 증적 없이는 판정 불가).
2. 한줄결함 형식: `[기준번호] [관찰 사실(원문 인용·URL)] [근거 조문] [우선순위 P1~P3] [권고 조치]`.
3. 우선순위: P1 법 위반·인증 불가 사유(2주), P2 심사 결함 확실(1개월), P3 개선 권고(3개월).

**산출**: `templates/06_mock-audit-report.md`
**게이트 G4 — 적대적 교차검증**: 작성자와 다른 사람(또는 별도 세션·프로필, 102 역할)이 결함 하나하나를 **반박**한다. 반박을 못 이긴 결함은 "확인 필요"로 강등하거나 삭제. 검증 기록은 `review/cross-check.md`에 남긴다.

---

## 6. Phase 5 — 분석보고서 통합 (0.5일)

**작업**
1. `templates/01_analysis-report.md`: 경영진 요약(1쪽) → 핵심 위험 5개 → 6종 문서 요약 → 조치 로드맵(2주/1개월/3개월) → 비용·기간 제안.
2. 모든 수치·사실에 근거 각주. 추정은 "추정"이라고 쓴다.

**게이트 G5**: `quality/qa-gate.md` 전 항목 통과. 점수는 `quality/scoring.md`로 산정해 70점 미만이면 전달 금지.

---

## 7. Phase 6 — 승인 및 전달

1. 전달본은 PDF로 변환하고 파일명에 버전·날짜를 넣는다. 원본(md)은 케이스 폴더에 보관.
2. **사람 승인 게이트**: 승인자 이름·일시를 `delivery/approval.md`에 기록한 뒤에만 발송.
3. 발송 후 고객 피드백·질의를 `delivery/feedback.md`에 기록 → `improvement/BACKLOG.md`에 반영.

---

## 8. Phase 7 — 사후 (고도화·현행화 모드)

기존 문서가 있는 고객은 Phase 2~4를 "대조" 중심으로 수행한다.
- 변경 대조표(기존→개정)를 모든 산출물에 포함.
- 법령 개정 이후 바뀐 항목만 따로 표시("개정 반영 필요").
- 흐름도는 기존 도면을 유지하되 노드 추가·삭제만 표시.

## 9. 시간·품질 기준 (표준 납기)

| 범위 | 표준 납기 | 비고 |
|---|---|---|
| 처리방침 평가만 | 3영업일 | Phase 0~2 + 5 |
| 평가 + 흐름표·흐름도 | 5영업일 | Phase 0~3 + 5 |
| 전체 6종 (모의심사 포함) | 7영업일 | 인터뷰 1회 포함 |

## 10. 금지 사항

- 근거 없는 지적, 법 조문 번호 추측 기재
- 로그인·인증·결제·폼 제출·취약점 스캔 등 능동 행위
- 고객 자료를 케이스 폴더 밖(채팅·메일 본문·공개 저장소)에 복사
- 승인 기록 없는 전달
- 로켓보안이 컨설팅한 기업의 인증심사 참여(이해충돌)
